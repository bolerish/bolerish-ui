# 프로젝트 검색과 필터

여러 검색 조건을 조정하는 동안 결과가 바뀌지 않아 선택을 마친 뒤 목록을 확인할 수 있습니다. 입력 중인 조건과 적용한 조건을 구분해, 현재 결과가 어떤 선택에서 나왔는지도 알 수 있습니다.

## 언제 반영할지 선택하기

| 사용 상황                              | 권장 선택                | 선택 이유                                                    |
| -------------------------------------- | ------------------------ | ------------------------------------------------------------ |
| 검색 입력 하나로 거르는 짧은 로컬 목록 | 즉시 반영                | 글자마다 처리해도 부담이 작고 결과 변화를 따라가기 쉬움      |
| 여러 조건을 함께 조정하는 목록         | 적용 버튼                | 중간 선택마다 결과가 반복해서 바뀌지 않음                    |
| 입력하면서 서버를 검색하는 목록        | 잠시 기다린 뒤 즉시 반영 | 요청 수를 줄이며, 이전 요청 취소나 오래된 응답 무시도 필요함 |

예제는 **Apply filters**를 사용합니다. 조건 수정과 결과 반영의 차이를 확인할 수 있도록 로컬 데이터를 사용합니다. 서버 검색 구현이 아닌 컴포넌트 조합 예제입니다.

## 직접 확인하기

1. **Archived**를 선택합니다. 결과와 적용 조건 요약은 여전히 전체 프로젝트 네 개를 보여 주고, 반영하지 않은 변경이 있음을 알립니다.
2. **Apply filters**를 누릅니다. 보관된 프로젝트 두 개만 남고 요약도 **Archived**로 바뀝니다.
3. **Customer**를 입력하고 Enter를 누릅니다. 일치하는 보관 프로젝트가 없어도 입력과 적용 조건 요약은 유지됩니다.
4. **Clear filters**를 누릅니다. 입력 중인 조건과 적용 조건을 즉시 함께 초기화하고 전체 네 개를 보여 줍니다.

# Search and filter projects

Let people finish adjusting several criteria before the results change. Separating draft and applied filters also makes it clear which choices produced the list currently on screen.

## Choose when changes apply

| Situation                                   | Recommended choice          | Rationale                                                                |
| ------------------------------------------- | --------------------------- | ------------------------------------------------------------------------ |
| A short local list with one search field    | Immediate filtering         | Each keystroke is inexpensive and the result is easy to follow           |
| Several criteria that users adjust together | Apply filters               | Intermediate choices do not repeatedly replace the results               |
| Server search while typing                  | Delayed immediate filtering | Reduces requests; also requires cancellation or ignoring stale responses |

The example uses **Apply filters**. Its data is local so the difference between editing criteria and applying them is easy to inspect. This is a composition example, not a server search implementation.

## Try the interaction

1. Choose **Archived**. The results and applied-filter summary still show all four projects, and the page identifies unapplied changes.
2. Select **Apply filters**. Only the two archived projects remain. The summary now says **Archived**.
3. Enter **Customer** and press Enter. No archived project matches; the input and applied summary remain visible.
4. Select **Clear filters**. Both draft and applied filters reset immediately, restoring all four projects.

## 함께 바뀌어야 하는 상태

폼은 `query`와 `status`를 저장하고 결과 목록은 `applied`만 읽습니다. 적용하면 앞뒤 공백을 지운 검색어와 상태를 `applied`에 복사합니다. 초기화하면 양쪽을 함께 갱신합니다. 조건을 수정하는 동안에는 변경 사항이 아직 결과에 반영되지 않았다고 안내합니다.

`FieldLabel`로 입력 이름을 유지합니다. 상태 하나를 고르므로 `Select`를 사용합니다. 짧은 선택지 세 개에 `Combobox`의 검색은 불필요합니다. 이름과 상태 하나는 일반 목록으로 보여 주고, 여러 열을 비교해야 할 때 `Table`을 선택합니다.

결과 수와 적용 조건을 하나의 상태 알림으로 전달합니다. 목록이 바뀌어도 초점은 옮기지 않으며 기본 폼 동작으로 Enter 제출을 지원합니다. 항목 선택만으로 반영하지 않고 제출할 때만 입력 중인 조건을 적용합니다.

## 서버 결과로 확장하기

요청을 시작하면 마지막으로 성공한 목록과 적용 조건 요약을 유지하고, 로딩 중에는 이전 결과임을 알립니다. 새 결과가 성공할 때까지 요청한 조건을 별도로 추적합니다. 실패하면 입력을 보존하고 갱신 실패와 요청한 조건으로 재시도할 방법을 제공합니다. 요청 실패를 “결과 없음”으로 표시하지 않습니다.

이전 요청이 끝나기 전에 새 요청을 보낼 수 있다면 이전 요청을 취소하거나 그 응답을 무시합니다. 새 조건을 적용할 때 페이지 번호를 초기화합니다. 결과를 공유해야 한다면 적용 조건을 URL에 담고 브라우저 탐색 시 폼과 결과를 함께 복원합니다.

## What stays in sync

The form stores `query` and `status`. The result list reads only `applied`. Applying copies the trimmed query and status into `applied`; clearing updates both sets of values. This avoids a list showing one filter while its controls appear to describe another.

Input names remain visible through `FieldLabel`. `Select` represents one status value; `Combobox` would add unnecessary search for three short options. A plain list suits names and one status; use `Table` when users need to compare several columns.

The result count and applied criteria share a status announcement. The list updates without moving focus, and the native form supports Enter to apply. Only submit applies draft changes; selecting an option does not.

## Extend to remote results

When a request starts, retain the last successful rows and their applied summary, and label them as previous results while loading. Track the submitted criteria separately until their results succeed. On failure, retain the draft, explain that the update failed, and offer Retry for the submitted criteria. Do not display “No results” for a failed request.

If newer requests can start before earlier ones finish, cancel the earlier request or ignore its response. Reset pagination when new filters are applied. For shareable results, serialize applied criteria into the URL and restore the form and results together on browser navigation.
