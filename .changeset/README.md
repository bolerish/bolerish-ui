# Package releases

`@bolerish/ui` and `@bolerish/tokens` form one fixed release group. A change to
one releases both at the same version. `@bolerish/lint` is versioned
independently, as is `@bolerish/docs-mcp`. The documentation MCP bundles a
build-time reference snapshot; rebuild it before preparing a release.
`@bolerish/lint` replaces `@bolerish/eslint-plugin-ui`; the former
package is not a compatibility alias. Docs and the root workspace are private
applications, not npm releases.

## Record and review a release

1. Run `pnpm changeset` after a user-facing package change. Describe the resulting
   behavior and any migration; choose the affected package and bump type.
2. Run `pnpm release:status` to review the dependency-aware release plan.
3. Run `pnpm version:packages` when preparing a release. It updates package
   versions, package changelogs and the workspace lockfile. Review these together.
4. Commit the reviewed package changelogs, manifests, lockfile and consumed
   changeset deletions together. Do not duplicate notes in the root changelog.
   Root and docs versions do not need to match UI.
5. Publishing is a separate action: `pnpm release` runs repository checks,
   tests, package verification and the docs build before `changeset publish`.
   It publishes only public packages whose versions are absent from npm.

Automatic Publish runs remain disabled for UI/tokens during development. Manual
Publish dispatches require a successful Verify run on the exact release commit. The lint
plugin is released independently. Prepare a release checkout containing only
its Changesets, run `pnpm version:packages`, then verify its tests and packed
artifact before publishing
with `pnpm --filter @bolerish/lint publish --access public`.
UI/tokens publication still requires explicit authorization. Docs previews the
current workspace API and can be deployed independently.

## UI/tokens publication resumption

Resume publication only after the full default/light token-map equality check
and documentation Default-example axe audits pass in CI.
Keep the existing keyboard contracts in that CI run. Meeting these gates does
not publish a release: decide and authorize the actual deployment separately.

The Publish workflow can be dispatched manually after the CI gates pass. Legacy
`vX.Y.Z` tag events remain disabled for publication. Changesets also creates
package-specific tags when publishing; those do not trigger publication.
GitHub Actions publishes the verified pnpm-packed UI/tokens archives through npm
Trusted Publishing (OIDC). Configure both packages for `bolerish/bolerish-ui` and
`publish.yml`; no `NPM_TOKEN` is required. Preparing versions does not publish.
A published release is immutable: corrections require another changeset/version.

Run `pnpm test:release` to verify the release policy with the colocated
`.changeset/release.test.ts` integration test.

## Compatibility and dependencies

- During 0.x development, use patch for compatible fixes and minor for additions
  or breaking API changes. Identify removals and required migrations explicitly;
  Changesets cannot infer semantic compatibility. After 1.0, breaking changes
  require a major release.
- Keep `@bolerish/ui` → `@bolerish/tokens` as `workspace:*`. pnpm packs it as the
  exact released token version. Publishing tokens does not update an already
  installed UI; consumers choose when to upgrade their installed package/lockfile.
- Package source may use workspace dependencies. Consumer apps should install
  published versions rather than import this repository's source directly.
  Docs intentionally previews the current workspace source.
- `catalog:` coordinates development dependency versions; it is separate from
  package versions and release groups. Updating external dependencies requires
  checking their effect on the published API and runtime behavior.
- The lint plugin is public and independent of the fixed group. Its packed
  artifact and standalone consumer are covered by release verification.

Changeset files are the only authored package release notes. Package changelogs
are generated by Changesets; the root changelog links to those packages and
preserves historical releases. Documentation-app-only work belongs in the
documentation and project work records, not npm package release notes.
